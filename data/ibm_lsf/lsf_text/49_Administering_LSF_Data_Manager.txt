Administering IBM Spectrum LSF Data Manager
The administrator of IBM Spectrum LSF Data Manager is an LSF administrator who performs tasks that are speciﬁc to LSF Data Manager.
Managing the dmd daemon
 An LSF data manager host is an LSF server host that is conﬁgured to run the LSF data manager daemon. The dmd daemon communicates with
the clusters it serves, and manages the transfer of data between source repository for data requirements and the execution environment of
jobs that have data requirements.
Managing the staging area (cache)
 A staging area (or data cache) is a managed ﬁle system on a data transfer (I/O) node or a mounted directory that is local to the cluster
compute nodes that access it. The staging area stores input ﬁles that are to be staged in for job execution or job output ﬁles to be staged out
to the source repository after the job ﬁnishes. Each staging area is managed by a single LSF data manager. Each cluster deﬁnes an LSF data
manager and the staging area that it manages.
Managing data transfer
 Conﬁgure and manage data transfer nodes and the queue that serves them. All data transfers are managed as LSF jobs. You can control both
the number of concurrent transfers and the priority of transfers in the data transfer queue. For example, you can conﬁgure fair share between
users in the data transfer queue.
Data speciﬁcation ﬁles
 A data speciﬁcation ﬁle is a text ﬁle that is used for staging a large number of data requirement ﬁles at one time through LSF Data Manager.
Each line in a data speciﬁcation ﬁle speciﬁes the name of a data tag or the path to a source ﬁle to be transferred to the staging area before a
job is submitted and scheduled. The tag or path can point to a ﬁle or a directory.
Conﬁguring IBM Spectrum LSF Data Manager to use the IBM Spectrum LSF multicluster capability
 LSF Data Manager integrates with existing forwarding policies in the LSF multicluster capability to ensure that the availability of data
requirements take precedence over availability of slots.
Managing the dmd daemon
An LSF data manager host is an LSF server host that is conﬁgured to run the LSF data manager daemon. The dmd daemon communicates with the
clusters it serves, and manages the transfer of data between source repository for data requirements and the execution environment of jobs that
have data requirements.
LSF data manager log ﬁle
The LSF data manager log ﬁle is named dmd.log.cluster_name. It is located in the directory that is deﬁned by the LSF_LOGDIR parameter in the
lsf.conf ﬁle.
dmd daemon operations
Important: Conﬁgure the LSF data manager host as an LSF server host to enable the dmd daemon to start automatically when LIM starts.
The LSF data manager has the following functions:
Receives data requirement information from the mbatchd daemon on the LSF management host to manage data movement. LSF data
manager either uses data already in the cache, or submits data transfer jobs to fetch data ﬁles.
Responds to data movement requirements from the bstage command to move data to a user-speciﬁed location.
Manages the lifecycle of cached data, and cleans up ﬁles with an expired grace period.
Queries remote peers to collect data availability information for job data requirements.
Sets the status for a data requirement ﬁle (STAGING, TRANSFERRED, or ERROR).
Query the LSF data manager with the bdata command to get information about data requirements ﬁles, LSF data manager conﬁguration, cluster
connections, transfer status, and other information. Administrators can use bdata command to reconﬁgure and shut down the dmd daemon.
How the dmd daemon starts
Conﬁgure an LSF server as an LSF data manager host (the LSF_DATA_HOSTS parameter in the lsf.conf ﬁle) so that thedmd daemon is automatically
started when LIM starts.

Conﬁguring LSF data manager failover
Similar to LSF management host failover, you can conﬁgure failover for LSF data manager hosts.
Procedure
Conﬁgure a list of candidate hosts in the LSF_DATA_HOSTS parameter in the lsf.conf ﬁle.
The LSF_DATA_HOSTS parameter speciﬁes a list of hosts where the LSF data manager daemon (dmd) can run, and where clients can contact the LSF
data manager that is associated with the cluster. The dmd daemon can run only on the listed hosts. All data manager candidate hosts must mount
the staging area at the same local path.
The order of host names in the list decides which host is the LSF data manager management host, and order of failover. All host names must be listed
in the same order for all LSF data managers.
Tip: You should list hosts in the LSF_DATA_HOSTS parameter the reverse order to the hosts listed in the LSF_MASTER_LIST parameter in the lsf.conf
ﬁle. Listing hosts this way helps to make sure that the current LSF management host is not the same host as the LSF data manager management
host.
Managing the staging area (cache)
A staging area (or data cache) is a managed ﬁle system on a data transfer (I/O) node or a mounted directory that is local to the cluster compute
nodes that access it. The staging area stores input ﬁles that are to be staged in for job execution or job output ﬁles to be staged out to the source
repository after the job ﬁnishes. Each staging area is managed by a single LSF data manager. Each cluster deﬁnes an LSF data manager and the
staging area that it manages.
Staging area operations
Every cluster that shares a staging area communicates with the same LSF data manager. The clusters query the LSF data manager for the availability
of data ﬁles. If the ﬁles aren't in the cache, the LSF data manager stages them in and notiﬁes the cluster when the requested data for the job is ready.
After ﬁles are staged in, the bstage in command copies or symbolically links them from the staging area to the job execution working directory.

When the CACHE_ACCESS_CONTROL = Y parameter is conﬁgured, the permissions on the ﬁles depend on whether the job is
submitted with the -datagrp option. If the –datagrp option is not speciﬁed, the permissions on the ﬁles are u+r. Only the original

to change the user group of the ﬁles, the permission on the ﬁles are ug+r. The original user and anyone who belongs to the
appropriate user group can access the ﬁles in the cache.
For data transfer jobs, the directory that contains the actual ﬁle data acts as the working directory for the transfer job. The directory
also contains the data transfer job script that is generated by dmd.

Where host_name, path, and hash come from the source host of the ﬁle.

user. user_name is included if CACHE_PERMISSIONS=user, and group_name is included if CACHE_PERMISSIONS=group.

Remote ﬁle access
LSF data manager attempts to resolve the location of required ﬁles by checking the entries in /etc/mtab and by using the ssh command.
1. Check the entries in /etc/mtab to see whether any of the mounted ﬁle system source locations is a preﬁx of host_name:path. If so, replace
this preﬁx with the local mount point for the source location that is speciﬁed in /etc/mtab and access the ﬁle at the resulting path.
2. If no such preﬁx is found, LSF data manager uses remote ssh execution to host_name to attempt the ﬁle read operation.
For data requirements submitted with the bsub command, if both of these checks fail, LSF data manager accepts the job anyway. For data
requirements speciﬁed with the bstage in command, if both of these checks fail, the bstage in command returns an error.

Conﬁgure user group cache access control
Enable LSF data manager cache access control with the CACHE_ACCESS_CONTROL=Y parameter.
The following parameters must be conﬁgured in the lsf.datamanager ﬁle to change user group access to your cached ﬁles:
CACHE_ACCESS_CONTROL=Y
Enables the owner of a data tag or a data ﬁle in the cache to change the user group ownership of a tag, an ownership, and the permissions of a
ﬁle. The bdata showconf command shows the setting of this parameter.
CACHE_PERMISSIONS=all
Sets ﬁle permissions and ownership of the LSF data manager staging area subdirectories. The all value ensures that LSF data manager keeps
only one copy of each ﬁle in the staging area to be shared by all jobs. Only a single cache is created for incoming ﬁles, and ﬁles are shareable
by all users.
CACHE_ACCESSIBLE_FILES= Y
Speciﬁes whether LSF data manager initiates a transfer job or creates a symbolic link from the cache to the requested data ﬁle.
Staging in jobs associated with another user's tags
By default, users can stage in ﬁles that are associated only with their own tags. Use the -u user_name option to stage in ﬁles that are associated with
tags that belong to another user name. The CACHE_ACCESS_CONTROL = Y parameter must be conﬁgured in the lsf.datamanager ﬁle to use the -u
option.
You must make sure that the tag exists and that you have appropriate permission to use the ﬁles associated with that tag before you submit your job.
Staging out jobs associated with another user's tags
By default, when a job stages out ﬁles to a tag, the tag directory is only accessible by the user who submitted the job. When the
CACHE_ACCESS_CONTROL = Y parameter is conﬁgured in the lsf.datamanager ﬁle, use the –g option to change the group that is associated with the
tag. The user_group_name argument speciﬁes the user group name to be associated with the tag. The permissions on the tag directory and its
contents are set so that the speciﬁed group can access the ﬁles.

Data transfer jobs
One data transfer job is submitted by LSF data manager for each ﬁle that needs to be transferred.
A transfer job is submitted to LSF for ﬁles that are not in STAGING or TRANSFERRED status. The LSF data manager creates a number of executable
scripts for the transfer job under the ﬁle cache directory. These scripts are submitted to LSF for execution:
Each script contains the ﬁle transfer command that is conﬁgured by the FILE_TRANSFER_CMD parameter in the lsf.datamanager ﬁle.
LSF data manager maintains information in the cache about the state of the transfer.
The queue of the transfer job is the queue that deﬁnes the DATA_TRANSFER=Y parameter in the lsb.queues ﬁle.
The environment for the transfer job can be changed by the ﬁle transfer command.
The transfer job runs as the execution user of the data job that triggered it.
The submission host of the transfer job is the current mbatchd management host.
The current working directory of the transfer job is the same as the ultimate cache location of the transferred ﬁle.
Transfer jobs cannot be requeued (brequeue).
If the command speciﬁed by the FILE_TRANSFER_CMD parameter does not exist on the data transfer node, or it is not executable by the
transfer job user, the transfer job exits with a special exit code 100.
LSF does not use any other job-level options. You cannot modify a data transfer job.
The DEFAULT_USER_GROUP and DEFAULT_PROJECT parameters apply to transfer jobs. The following default LSF parameters do not apply to
transfer jobs:
DEFAULT_JOB_CWD
A current working directory speciﬁc to LSF data manager is required for transfer jobs.
DEFAULT_JOB_OUTDIR
The output directory is not set for transfer jobs.
DEFAULT_JOBGROUP
The job group that the transfer job is submitted to cannot be a default job group.
DEFAULT_QUEUE
The data transfer queue that the transfer job is submitted to cannot be a default queue.

LSF data manager transfer queue
All transfer jobs that are requested by LSF data manager for that cluster go to this queue. LSF data manager is enabled with the LSF_DATA_HOSTS
parameter in lsf.conf. Conﬁgure the data transfer queue and manage jobs in the queue.
Only one queue in a cluster can be a data transfer queue.
Regular jobs that are submitted to this queue through bsub are rejected.
Use bstop, bresume, and bkill commands to stop, resume, and kill your own jobs in a data transfer queue. Additionally, LSF administrators and
queue administrators can use the btop and bbot commands to move jobs in the queue. All other commands on jobs in a data transfer queue are
rejected. Jobs from other queues cannot be switched to a data transfer queue (bswitch).
You cannot use the following queue parameters in a data transfer queue:
INTERACTIVE=ONLY
RCVJOBS_FROM
MAX_RSCHED_TIME
SUCCESS_EXIT_VALUES
RERUNNABLE
The data transfer queue cannot appear in the list of default queues that are deﬁned by the DEFAULT_QUEUE parameter that is deﬁned in the
lsb.params ﬁle. Jobs that are submitted to the data transfer queue are not attached to the application speciﬁed by the DEFAULT_APPLICATION
parameter that is deﬁned in the lsb.params ﬁle.
If you are using the IBM Spectrum LSF multicluster capability (LSF multicluster capability) and the execution cluster with LSF data manager runs in a
public-cloud infrastructure, the forwarded job’s data requirements from the submission cluster are pushed to the execution cluster and the
forwarding job's output is pulled back from the submission cluster. The execution cluster requests to access the submission cluster for handling the
data transfer.
To facilitate these data requirements, enable an LSF data manager data transfer queue as a remote send-jobs queue in the execution cluster and
enable the corresponding receive-jobs queue in the submission cluster to pull output data from the execution cluster.
If you specify a remote queue with the SNDJOBS_TO parameter in the data transfer queue in the execution cluster, the path of the
FILE_TRANSFER_CMD parameter must exist in the submission cluster. You must also add the execution cluster to the RCVJOBS_FROM parameter (or
use the allclusters keyword) for the remote queue in the submission cluster to pull output data from the execution cluster.
The data transfer queue in the public cloud execution cluster must specify all possible remote cluster names in the SNDJOBS_TO parameter. The
receive-jobs queue of the submission cluster, which cannot be the local data transfer queue, shares the same set of transfer nodes and must include
the execution cluster name (or the allclusters keyword) in the RCVJOBS_FROM parameter.
If you change the data transfer queue to another queue, transfer jobs that were in the original queue remain in that queue and are scheduled and run
as normal. New transfer jobs are submitted to the new queue. The LSF data manager is notiﬁed of the success or failure of these jobs.

Conﬁguring the data transfer queue
The DATA_TRANSFER parameter in the lsb.queues ﬁle conﬁgures a queue as the data transfer queue for LSF data management.
About this task
All transfers are managed as LSF jobs that run in a dedicated data transfer queue. LSF generates a transfer job for each unique ﬁle and places the job
into the transfer queue. The transfer job runs the conﬁgured transfer command on data transfer hosts allocated to the transfer queue to moves the
data from its source to its destination.
Procedure
IBM Spectrum LSF 2149

1. Specify the DATA_TRANSFER=Y parameter in the lsb.queues ﬁle to enable a dedicated queue for data transfer jobs.
If you are using the IBM Spectrum LSF multicluster capability, enable the data transfer queue in the execution cluster.
2. If you are using the IBM Spectrum LSF multicluster capability (LSF multicluster capability) and the execution cluster with LSF data manager
runs in a public-cloud infrastructure, conﬁgure environment so that the submission cluster pushes the forwarding jobs' data requirements to
the execution cluster and pulls the forwarding jobs' output data back from the execution cluster.
a. For the data transfer queue in the execution cluster, specify the SNDJOBS_TO parameter to include a remote queue from the
submission cluster.
This remote queue on the submission cluster is the receive-jobs queue that pushes the data requirements to the execution cluster and
pulls the output data back from the execution cluster.
b. For the receive-jobs queue in the submission cluster, specify the RCVJOBS_FROM parameter to include the execution cluster.
You can also include the allclusters keyword, which includes the execution cluster.
3. Specify other queue parameters to set appropriate scheduling policies for your site.
For example:
The following queue is conﬁgured as a high-priority preemptive queue that serves four hosts.
Begin Queue 
QUEUE_NAME    = transfer 
PRIORITY      = 100 
DATA_TRANSFER = Y 
PREEMPTION    = PREEMPTIVE 
HOSTS = hostA hostB hostD hostX 
If you are using the LSF multicluster capability, the following queue is conﬁgured in the execution cluster clusterE, which runs in a
public-cloud infrastructure and has the LSF data manager transfer queue data_transfer set as a remote send-jobs queue to the
receive_q queue in the submission cluster clusterS:
Begin Queue 
QUEUE_NAME=data_transfer 
DATA_TRANSFER=Y 
SNDJOBS_TO=receive_q@clusterS 
HOSTS=hostS1 hostS2 # Transfer nodes in the execution cluster 
End Queue
The receive-jobs queue receive_q is conﬁgured in the submission cluster clusterS to accept jobs from (and push data to) the
execution cluster clusterE:
Begin Queue 
QUEUE_NAME=receive_q 
RCVJOBS_FROM=clusterE 
PRIORITY=40 
HOSTS=hostS1 hostS2 # Transfer nodes in the submission cluster 
RES_REQ=select[type==any] 
End Queue

Each cluster that uses LSF data management must have a set of hosts that act as data transfer nodes (also referred to as I/O nodes). Data transfer
nodes are execution hosts for transfer job that LSF data manager submits to a data transfer queue.
Data transfer nodes must have the following properties:
Data transfer nodes must statically mount the staging area at the same location as the LSF data manager.
Data transfer nodes must be conﬁgured as LSF execution hosts in the data transfer queue.
For input data requirements (data stage in), data transfer nodes must be able to reach the data source location through the conﬁgured data
transfer tool.
For output data requirements (data stage out), data transfer nodes must be able to reach the data destination location through the conﬁgured
transfer tool.
The transfer command (speciﬁed by the FILE_TRANSFER_CMD parameter in the lsf.datamanager ﬁle) must be executable from the data
transfer node. If the transfer command is not executable, the transfer job exits with special exit code 100.
LSF expects that a new ﬁle or directory that is created in the cache area is accessible from any data transfer node within 1 minute.
Troubleshoot data transfer job failure
If a data transfer job execution fails, jobs that require the ﬁle that the transfer job is transferring are killed by LSF.
Use the bjobs -l command to see the following information about the job:
The job exits with code 125.
The TERM_DATA job exit reason.
The external message posted to the job.

Script interface for data transfer jobs
LSF data manager administrators provide a customized data transfer command that is speciﬁed by the FILE_TRANSFER_CMD parameter in
lsf.datamanager used by data transfer jobs.
Requirements of the data transfer command
The command must take two arguments with the following form:
[host_name:]abs_file_path
The ﬁrst argument is an absolute path to the location of the source ﬁle and the second is absolute path to the destination of the transfer.

The command that you specify must block until the transfer is successfully completed or an error occurs.
The command must return 0 if successful, and a nonzero value if an error occurs.
The command must be executable by users from the cluster data transfer nodes.
The command must be able to accept path descriptors with or without host names for each of its two arguments. For example, the default scp
command satisﬁes both requirements. The cp command is not valid because it can't accept a host name.
If the command returns successfully, LSF data manager assumes that the transfer was completed without error
The default transfer command (/usr/bin/scp) meets these requirements under the following conditions:
The data transfer nodes are standard Linux hosts with scp deployed
Passwordless SSH is conﬁgured for users from the data node to the data source and destination hosts.
Important: If a transfer job that is submitted by LSF data manager fails, it is not retried. Any jobs that request the data ﬁle being transferred by the
failed job are killed by LSF with exit code 125.
Example data transfer wrapper script
Depending on the transfer tool you are using, you might want to implement a wrapper script to help you debug data transfer problems, and to make
data transfers more resilient to failure. The following example wrapper script for the scp command does two things:
Retry the transfer up to ﬁve times before it gives up, sleeping 10 seconds between retries
Log any error messages output by the scp command to the ﬁle /tmp/<transfer_jobid>.<host_name>.err on the data transfer node (I/O node)
that ran the transfer job
#!/bin/bash  
# 
# Save the source, destination, and execution host 
# 
src=$1 
dst=$2 
host='hostname' 
# 
# File names for the error log and a temp file 
# 
errlog=/tmp/$LSB_JOBID.$host.err 
tmplog=/tmp/$LSB_JOBID.tmp  
# 
# Append the source and destination of the transfer to the error log 
# 
echo "SRC = $src" >> $errlog 
echo "DST = $dst" >> $errlog  
# 
# Try to do the transfer up to 5 times, sleeping 10 seconds in between 
# 
ntries=$((0)) 
done=$((0)) 
while [[ $(($ntries < 5)) == 1 && $(($done == 0)) == 1 ]]; do 
    # 
    # Increment the retry count 
    # 
    ntries=$(($ntries + 1)) 
    # 
    # Run the transfer command and store its output in a temp file 
    # 
    scp $src $dst &> $tmplog 
    # 
    # Save the error code returned by the command 
    # 
    code=$? 
    if [ $code == "0" ]; then 
        # 
        # Success!   Delete the error log and break out of the loop 
        # 
        rm $errlog 
        done=$((1)) 
     else 
        # 
        # Failure :( Append the command output to the error log 
        # 
        echo "==== OUTPUT: (Attempt $ntries) ===================" >> $errlog 
        cat $tmplog >> $errlog 
    fi 
    # 
    # Sleep for 10 seconds before trying again
